# 육지 시간별 SMP · 자사 발전기 이용률 전망 시스템

> 프로젝트 기획서 겸 작업 지시서. VS Code에서 이 파일을 README로 두고 시작.
> 최종 수정: 2026-09-11

---

## 1. 목적과 산출물

시간별로 다음 두 가지를 전망하고, 그 정확도를 매달 자동으로 채점하는 시스템을 만든다.

| 산출물 | 단위 | 용도 |
|---|---|---|
| 육지 시간별 SMP | 원/kWh, 시간별 | 월간 전망 업무, 시장 분석 |
| 자사 호기별 이용률 | %, 호기·시간별 | 수익 전망, 연료 조달, 정비 계획 |
| 정산수익 전망 | 원, 월별 | 최종 KPI |
| 오차 분해 리포트 | 월별 | 다음 달 개선 지점 특정 |

전망은 **단일 숫자가 아니라 범위**로 낸다. (예: 이용률 54~71%, 중앙값 62%)

---

## 2. 전제: SMP와 이용률은 같은 계산에서 나온다

전력거래소는 연료비가 싼 발전기부터 순서대로 켠다. 마지막에 켜진 발전기의 변동비가 그 시간의 SMP다. 같은 그림에서 우리 호기가 그 선 안에 들어왔는지도 결정된다.

```
        연료비
          ↑
          │                                    ┌──── 유류
          │                          ┌──LNG하위┘
          │                 ┌─LNG중위┘
          │            ┌우리┘                    ← 여기가 SMP
          │      ┌LNG상┘
          │  ┌석탄┘
          │┌─┘ 원자력
          └──────────────┬──────────────────→ 누적 설비용량
                      수요
```

따라서 이용률은 세 덩어리의 합이다.

1. **경제급전 시간** — SMP > 자사 변동비인 시간 (몸통)
2. **제약운전 시간** — 계통 사정으로 가격과 무관하게 도는 시간 (당진 지역 특성상 무시 못 함)
3. **불가동 시간** — 계획정비 + 불시고장 (차감)

여기에 기동 제약(최소 운전·정지시간, 기동비)이 얹힌다. **가격이 잠깐 올라도 켜지 않는 게 이득인 구간**이 존재하므로 이 판단 로직이 없으면 중간 계절 이용률이 크게 틀린다.

## 3. M-Core와의 역할 분담 ★핵심 설계 결정

사내에 이미 SMP·이용률 전망 시스템 **M-Core**가 있다. 확인된 사실:

- 결과가 **시간대별**로 나온다
- **언제든 재실행 가능**한 구조다

→ 독립 재구축(중복 투자, 사내 숫자 이원화)도, 단순 출력 보정(가정 오차를 엔진 오차로 오인)도 아닌 **층 분리** 방식을 택한다.

```
┌─────────────────────────────────────────────┐
│  M-Core  (급전 시뮬레이션 엔진 — 그대로 활용)  │
└───────────────┬─────────────────────────────┘
                │ 시간별 SMP, 발전계획
    ┌───────────┼───────────┬──────────────┐
    ▼           ▼           ▼              ▼
 입력감사층   출력보정층   시나리오래퍼   자사호기 이용률 모델
 (가정 검증)  (잔여편향)   (N회 재실행)   (우리가 직접 구축)
    │           │           │              │
    └───────────┴─────┬─────┴──────────────┘
                      ▼
           최종 전망 (중앙값 + 범위) → 정산수익
```

### 3-1. 입력 감사층 — 가장 먼저, 가장 값싼 개선
M-Core 오차의 대부분은 엔진이 아니라 **넣은 가정**에서 온다. 월 오차를 요인별로 분해한다.

```
전체 오차 5.2원 = 수요 가정 3.1원 + 연료단가 가정 1.4원
                 + 정비일정 0.4원 + 엔진 고유 0.3원
```

방법: 가정을 하나씩 실적값으로 교체해 재실행 → 오차 감소분 측정. (재실행 가능하므로 구현 가능)

### 3-2. 출력 보정층 — 남은 편향만
가정 오차를 걷어내고 남은 **엔진 고유 편향**만 보정한다. 보통 시간대별·계절별·수요구간별로 일정한 치우침이 남는다. 여기에 전체 오차를 통으로 학습시키면 안 된다 — 가스가 쌌던 시기에 학습한 보정값이 비싼 시기에 반대로 작동한다.

### 3-3. 시나리오 래퍼 — 단일값을 범위로
기온·연료단가·원전정비·고장을 흔들며 M-Core를 N회 재실행 → 분포 산출.
우리 호기가 한계기 근처에 있을수록 범위가 넓어지는데, **그 폭 자체가 경영 정보**다.

### 3-4. 자사 호기 이용률 모델 — 우리가 직접
여기는 우리가 정보 우위에 있다. M-Core가 정확히 알 수 없는 값들:
- 우리 LNG 실제 도입단가
- 호기별 실측 효율곡선(성능시험 기준)
- 기동비, 최소 운전·정지시간
- 실제 운전 관행

M-Core의 시간별 SMP를 **입력으로 받아** 우리 호기 가동 여부만 계산한다. 중복 없이 빈 곳만 채우는 구조.

### 3-5. 감시용 경량 모델
실적에서 역추정한 공급곡선(아래 4-3). M-Core와 크게 어긋날 때 경보만. **대체가 아니라 견제.**

### 4-2. 시장 발전기 정보 — 과소평가 금지

급전 시뮬레이션은 결국 **다른 발전기들을 줄 세운 그 줄**이다. 우리 호기는 그 줄 어딘가에 끼어 있을 뿐이므로, 줄이 부정확하면 SMP도 이용률도 같이 틀린다.

호기별 필요 항목: 정격용량 · 최소출력 · 연료종 · 연계지역 · **변동비** · 열소비율 · 예방정비 일정 · 강제정지율 · 신규준공/폐지 시점 · 필수운전 여부

작업량 줄이는 두 가지 방법:
- **우리 변동비 ±20원 구간만 정밀하게.** 원전·저가 석탄은 "무조건 도는 덩어리"로 뭉뚱그려도 결과가 거의 안 변한다. 작업량 1/10.
- **GS EPS는 시장참여자**이므로 KPX 시장운영시스템에서 일반 미공개 발전계획·가용용량·정비 자료 접근 권한이 있을 수 있다. 공공데이터포털보다 사내 경로를 먼저 확인.

### 4-3. 실적 역추정 공급곡선 (1단계에서 바로 가능)

호기 목록이 없어도 과거 **시간별 잔여수요 vs SMP 실적**을 산점도로 뿌리면 시장 전체 공급곡선 모양이 드러난다. 호기 자료가 들어오는 대로 정밀 모델로 갈아타되, 이 곡선은 검산 도구로 계속 남긴다.

### 4-4. 사내 자료 ★최대 병목

기술이 아니라 **부서 협조** 문제라 가장 오래 걸린다. 착수 즉시 요청할 것.

- 호기별 시간별 발전량 실적 (계량)
- 기동·정지 이력
- 성능시험 기준 효율곡선
- 최소출력, 최소 운전·정지시간, 기동비
- 정비 계획 및 고장 이력
- **우리 LNG 도입단가** ← 시장 평균으로 대체하면 급전순위가 통째로 틀려 이용률이 수 %p 어긋남
- 제약발전(SCON) 이력
- **M-Core 과거 전망 이력 + 그때의 입력 가정** (아래 8절 참조)

## 5. 자동 수집 아키텍처

Hostinger VPS(Ubuntu 22.04)에 배치. 기존 텔레그램 봇을 알림 채널로 재사용.

```
[cron / APScheduler]
   → collectors/*.py          API별 1파일
   → data/raw/YYYY/MM/DD/*.json   원본 무손실 보관
   → parse → DuckDB upsert
   → 품질검사 → 실패 시 텔레그램 알림
```

- **DB**: KVM1 사양이면 TimescaleDB보다 **DuckDB + Parquet**. 가볍고 백테스트 쿼리가 빠르다.
- **멱등성**: PK `(date, hour, market_type, unit_id)` 로 UPSERT. 재실행해도 중복 없음.
- **`market_type` 컬럼을 처음부터 넣을 것.** 실시간시장이 전국 확대되면 가격이 '하루전'/'실시간'으로 갈라진다.
- **재시도**: `tenacity` 지수백오프.
- **품질 게이트**: 하루 24행 존재 / SMP 범위(0~400) / 전일 대비 급변 플래그 / **결측은 임의 보간 금지, NaN 유지**.
- **백필 스크립트 분리**: `backfill.py --from 2015-01-01`. 2022 고유가·SMP상한제 구간은 더미 플래그.

### 수집 스케줄

| 시각 | 대상 |
|---|---|
| 매일 05:10 | 하루전 SMP + 수요예측 |
| 매시 :05 | 5분 수급현황 |
| 매일 06:00 / 18:00 | 기상 예보 |
| 매일 07:00 | 전일 자사 호기 실적 (자동 채점용) |
| 매주 월 | 정비 일정 변경분 |
| 매월 5일 | 연료단가, 발전기별 변동비, 설비 구성 |
| **전망 실행 시마다** | **M-Core 결과 + 입력 가정 스냅샷** |

## 6. 모델 구성 (4단)

한 덩어리로 만들지 않는다. 단계를 나눠야 틀렸을 때 어디가 틀렸는지 찾을 수 있다.

**1단 — 수요·재생에너지 예측**
기온·요일·연휴 → 시간별 수요, 태양광 발전량. 여기가 틀리면 뒤가 전부 틀리므로 정확도를 따로 관리.

**2단 — 급전 결과 확보**
M-Core 실행 (+ 감시용 역추정 공급곡선 병행). 출력: 시간별 SMP, 발전계획.

**3단 — 자사 호기 가동 판단**
M-Core SMP + 우리 변동비 + 기동 제약 → 호기별 시간별 출력. 기동비를 고려해 "켜는 게 이득인가"까지 판단.

**4단 — 보정 및 시나리오**
실적 기반 잔여편향 보정 + 가정을 흔들며 N회 반복 → 분포.

**벤치마크 (반드시 먼저 만들 것)**
- 지난주 같은 요일·같은 시간 값
- `LNG 열량단가 × 대표 열소비율`
- 무보정 M-Core 원본

이 셋을 못 이기면 어떤 개선도 개선이 아니다. 모든 성적표의 기준점.

## 7. 검증

### 7-1. 절대 규칙
- **정보 시점 고정.** D+1 예측이면 D일까지 입수 가능한 자료만. 기상은 실황이 아니라 **그때의 예보값**. 여기서 반칙하면 성적은 좋아지고 실전은 무너진다.
- **Walk-forward.** 과거 2년을 하루씩 밀며 재현. 랜덤 분할 금지(누수).

### 7-2. 지표

| 대상 | 지표 |
|---|---|
| SMP | MAE, RMSE, **rMAE**(벤치마크 대비 상대오차) |
| 이용률 | %p 오차, 월간 발전량 % 오차, **기동 횟수 적중** (연료 조달·설비 수명 직결) |
| 범위 예측 | pinball loss, PICP(90% 구간 실제 포함률), Winkler score |
| 최종 | **정산수익 예측 오차** ← 가격이 조금 틀려도 수익이 맞으면 실무상 성공 |

### 7-3. 분해 진단

- **오차 분해**: 시간대별 / 월별 / 피크·오프피크 / SMP 급등일. 평균만 보면 급등일 실패가 가려진다.
- **연결 검증**: 실적 SMP를 넣었을 때 이용률 오차 vs 예측 SMP를 넣었을 때 이용률 오차.
  - 앞이 크다 → 자사 호기 모델 문제
  - 뒤가 훨씬 크다 → SMP 예측 문제
- **입력 귀인**: 기온·연료비·원전정지를 하나씩 실적값으로 교체 → 오차 감소분 측정.
- **모형 비교는 Diebold-Mariano 검정으로.** MAE 0.3원 차이를 "개선"이라 부르지 않기 위해.

## 8. 오늘 당장 할 일

> **M-Core 전망 결과와 입력 가정을 매 실행마다 통째로 스냅샷 저장.**

보정층은 과거 전망 이력이 있어야 학습 가능한데, 대개 최신 결과만 덮어쓰여 있다. 3개월치면 오차 분해를 시작할 수 있고, 6개월치면 보정층 학습이 가능하다. **지금 안 쌓으면 6개월 뒤에도 같은 고민을 반복한다.**

저장 형식 예:
```
data/mcore/YYYYMMDD_HHMM/
  ├── assumptions.json    # 수요·연료단가·정비·설비 가정
  ├── output_hourly.csv   # 시간별 SMP, 호기별 발전계획
  └── meta.json           # 실행자, 목적, M-Core 버전
```

## 10. 12주 로드맵

| 주차 | 작업 | 산출물 |
|---|---|---|
| 0 | **M-Core 스냅샷 저장 시작** (즉시) | 이력 축적 개시 |
| 1 | API 운영계정 신청, 스키마 설계, 저장소 셋업 | `schema.sql` |
| 2 | 시장 공개자료 수집기 + 10년 백필 + 품질검사 | 자동 수집 가동 |
| 3 | **사내 자료 확보** (호기 실적·제약·정비·도입단가) | 최대 병목 |
| 4 | 역추정 공급곡선, 벤치마크 3종 | 기준점 확정 |
| 5 | 수요·태양광 예측 모델 (1단) | |
| 6 | M-Core 입력 감사층, 오차 요인 분해 | 개선 지점 특정 |
| 7 | 자사 호기 가동 모델 (3단) | |
| 8 | 기동 제약·기동비 로직 추가 | |
| 9 | 출력 보정층 (4단 전반) | |
| 10 | 시나리오 래퍼, 범위 예측 (4단 후반) | |
| 11 | 2년 walk-forward 채점, 연결 검증 | 성적표 |
| 12 | 발전량→연료량→정산수익 연결, 월간 리포트 자동화 | 운영 전환 |

**병목은 3주차.** 기술이 아니라 협조가 필요한 일이라 가장 오래 걸리고, 이게 없으면 7주차부터 멈춘다.

## 11. 확인 필요 사항

- [ ] M-Core 과거 전망 이력이 보관돼 있는가 (없으면 0주차부터 축적)
- [ ] M-Core 가정 변경 재실행을 스크립트로 자동화할 수 있는가 (수동이면 시나리오 N회가 비현실적)
- [ ] KPX 시장운영시스템에서 발전기 제원·정비 자료 접근 권한이 있는가
- [ ] 사내 계량 실적을 API/DB로 받을 수 있는가, 아니면 수동 추출인가
- [ ] 실시간시장 육지 확대 일정 (타깃 정의가 갈라지는 시점)

## 12. 참고

- **Lago et al. (2021), `epftoolbox`** — day-ahead 전력가격 예측 오픈 벤치마크. LEAR/DNN 구현체, 2년 out-of-sample + DM 검정 프로토콜을 그대로 차용 가능.
- **GEFCom2014 price track** — 확률예측 평가(pinball loss) 표준.
- **ENTSO-E Transparency Platform / `entsoe-py`** — 부하·발전·정비·가격 단일 API. 테이블 스키마 설계 참고.
- **영국 Elexon BMRS, 독일 SMARD** — 정비계획·REMIT 공시까지 공개. 사내 자료 확보 요청 시 근거 사례로 활용.
